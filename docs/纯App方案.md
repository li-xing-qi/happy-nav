# 只凭一个 App 能做到什么

> 老板的问题：没有服务器、没有电脑，只有一个 App，能做到什么地步？我们这套有没有可能？
>
> 结论先说：**能，而且质量几乎不降——因为"脑子"本来就不在服务器上。**
> 真正要搬的是"手脚"和"记性"，不是"智商"。

---

## 0. 先纠正一个前提：现在这台"服务器"在干什么

打开 `pm2 list` 能看到四个进程，但**没有一个在跑模型**：

| 进程 | 干什么 | 是不是"智能" |
|---|---|---|
| `wanxiang` | 站点（`yu.js` + `yu.html` + 静态文件 + 上传） | 不是，只是个房间服务器 |
| `dsh` | DeepSeek Harness，**调 DeepSeek 云端 API** 的 agent 运行时 | 不是，脑子在 DeepSeek 机房 |
| `yufish` | QQ ↔ 房间的桥 + 语音转写 | 不是，纯转发 |
| `tts 插件` | 转给 Breeze 云端合成 | 不是，声音在 Breeze 机房 |

也就是说：**这台 2 核 2G 的机器只是一个"中转站 + 记事本"**，它自己一点智能都没有。
真正贵的东西（DeepSeek 的模型、Breeze 的音色）本来就在别人的云上。

所以"只凭一个 App"不是"把大模型塞进手机"，而是：

> **把中转站和记事本搬进 App，让它直接跟云上的模型对话。**

这条路的质量和现在**一模一样**（同一个 API、同一个模型、同一套提示词），
只是省掉了中间那一跳，顺带省掉每月的机器钱和 easytier。

想让 App **彻底不联网**也能聊，才需要把模型搬进手机——那是另一条路，见第 4 节，
代价是质量下降 + 包体 1~3GB。

## 1. 服务器现在承担的 6 件事，逐项找替代

| # | 职责 | 现在怎么做 | App 内替代 | 难度 | 会丢什么 |
|---|---|---|---|---|---|
| 1 | **agent 循环**（收消息 → 拼上下文 → 调模型 → 解析工具调用 → 回话） | `dsh` + `AGENTS.md` + 插件 | Kotlin 重写一遍；或直接在 WebView 的 JS 里跑 | ★★★ | dsh 的插件生态（shell、文件、画图全废） |
| 2 | **房间与消息**（`/api/yu/*`、SSE、成员、表情） | `yu.js` + `data/yu/0000.json` | 内置一个"迷你 yu.js"，监听 `127.0.0.1`，**前端零改动** | ★★ | 多人房间、网页版、换手机不同步 |
| 3 | **记忆**（`chatlog.jsonl`、`MEMORY.md`、判官） | 文本文件 + 定时任务 | SQLite 三张表 + 启动时摘要 | ★★ | 无（反而更快，查询不读全文件） |
| 4 | **语音合成** | Breeze 云端（要 key、要网） | 本地 sherpa-onnx / Kokoro（离线）+ Breeze（在线，直连） | ★★ | 断网时音色从"大肥鱼"变"本地嗓" |
| 5 | **语音转写** | 服务器 whisper.cpp（3.3 秒） | 手机端 sherpa-onnx / SenseVoice（**更快，无上传**） | ★★ | 无（手机 NPU 比那台 2 核强得多） |
| 6 | **定时提醒 / 通知** | 服务器 cron 触发 → 推送 | `AlarmManager` + 本地通知 | ★ | 无（更准，不依赖网络） |

**唯一真正搬不走的**：QQ 那条线。OneBot 需要一个常开的账号在跑，手机做不到
（Android 会被 Doze 掐、QQ 协议也不允许）。所以：

- **要保留"她在 QQ 上也能找到你"** → 必须留一台常开的机器（哪怕是最便宜的小鸡）。
- **只在 App 里聊** → QQ 桥可以彻底删掉，`yufish.js` 那 700 行也不用维护了。

## 2. 最关键的一个设计：**内置迷你服务端，前端零改动**

现在的 `yu.html` 是纯前端，所有数据都走 `/api/yu/*`。这意味着：

> 只要 App 里起一个**监听 `127.0.0.1` 的小 HTTP 服务**，实现同样的 6 个接口，
> 页面一行都不用改，`yu.html` 直接跑在 `http://127.0.0.1:3000/yu` 上。

接口清单（都是现成的，照抄行为即可）：

```
GET  /api/yu/state?code&pid      房间快照（成员、消息、表情、贴纸）
GET  /api/yu/stream?code&pid     SSE（本地可以改成 1 秒轮询，省电又简单）
POST /api/yu/enter               进房间
POST /api/yu/send                {type:'text'|'voice'|'image'|'file', ...}
POST /api/yu/upload              附件（直接写 App 私有目录，连 HTTP 都不用）
POST /api/yu/act | ping | leave  状态
```

Kotlin 侧用 `ServerSocket` 手写一个 200 行的 HTTP/1.1 就够（不用引框架），
或者用 `NanoHTTPD`（单文件、无依赖）。**这一步是整个方案的地基**：
它让"重写 App"变成"补一个后端"，UI、气泡、表情、录音、通知全部现成。

存储用 SQLite：

```sql
msgs(id INTEGER PK, role TEXT, name TEXT, type TEXT, text TEXT, url TEXT,
     dur INT, ts INT, pid TEXT)
facts(id INTEGER PK, key TEXT, val TEXT, ts INT)      -- 长期事实
rules(id INTEGER PK, body TEXT, scope TEXT, ts INT)   -- 临时约定
kv(k TEXT PK, v TEXT)                                 -- 进度、设置、人设版本
```

### agent 循环（约 300 行 Kotlin）

```kotlin
suspend fun turn(userText: String): String {
    val ctx = buildContext(userText)          // 人设 + 最近 20 条 + 相关 facts + 时间
    var msgs = listOf(system(ctx), user(userText))
    repeat(4) {                                // 最多 4 轮工具调用
        val r = deepseek.chat(msgs, tools)     // 直连 api.deepseek.com，SSE 流式
        val call = r.toolCall ?: return r.text
        val out = tools.run(call)              // speak / remember / remind / search
        msgs = msgs + r.assistantMsg + toolResult(call.id, out)
    }
    return "……"
}
```

**关键**：这不是"重写 dsh"，是"只实现你真正用到的 4~5 个工具"。
现在 dsh 里挂了一堆（shell、文件、画图、网页），在手机上本来就没法用，砍掉正好。

### 人设与规则怎么远程更新（不需要服务器）

现在改 `AGENTS.md` 即时生效，是因为文件在服务器上。App 里改成：

```
启动时（有网）→ GET https://raw.githubusercontent.com/<你>/happy-nav/main/workspace.example/AGENTS.md
               → 存进 kv 表，带版本号；拉不到就用内置那份
```

GitHub raw 免费、无需鉴权、无需服务器。改人设 = 改仓库 + 发一次 commit，
App 下次启动自动生效。**这就是"无服务器但要能远程改"的标准做法。**

## 3. 方案 A：纯 App + 云 API（推荐，质量不降）

### 链路

```
APK
├── WebView（yu.html，原样）
├── 迷你 HTTP 服务（127.0.0.1:3000，实现 /api/yu/*）
├── SQLite（消息 / 事实 / 约定 / 设置）
├── Agent 循环（Kotlin）──HTTPS──→ api.deepseek.com
├── TTS：本地 sherpa-onnx（离线） / Breeze（在线，key 存 App）
├── STT：本地 sherpa-onnx（离线）
└── 通知 / 提醒：本地 AlarmManager
```

### 硬指标

| 项 | 数字 |
|---|---|
| APK 体积 | **约 6~9MB**（含前端与本地语音模型；不含大模型） |
| 首次启动 | 不下载模型 → 秒开；若下载本地 TTS/STT，约 200MB，一次性 |
| 内存占用 | 常驻 60~120MB（比现在 WebView 壳多 40MB 左右） |
| 回复延迟 | **比现在快**：少了一跳 easytier + 少了一次 dsh 中转，通常省 300~800ms |
| 断网 | 不能聊（但要离线聊就走方案 B） |
| 费用 | 机器钱 ¥0；API 按量，日常聊天约 **¥3~10/月**（DeepSeek 缓存命中后更便宜） |
| 开发量 | **P0 约 3~5 天**能跑通"纯 App 聊天 + 语音" |

### 这一版会丢的东西（说清楚）

1. **QQ 双向**——除非留一台常开机器。
2. **多人房间 / 网页版**——`0000` 房间变成"本机单人"，别人进不来。
3. **shell 类工具**——跑命令、改文件、画图，手机上没有沙箱，全砍。
4. **换手机要迁移**——SQLite 导出/导入（可做一键备份到网盘/相册目录）。

## 4. 方案 B：连模型也搬进手机（真·离线）

只有一种情况值得做：**你经常在没网的地方想跟她说话**（地铁、飞机、老家）。

### 能塞进手机的模型（2026 年的现实）

| 模型 | 量化后体积 | 8Gen2 上速度 | 8GB 手机 | 主观质量 |
|---|---|---|---|---|
| Qwen3-1.7B | ~1.1GB | 25~35 tok/s | 舒适 | 日常聊天够，长逻辑弱 |
| Qwen3-4B | ~2.4GB | 12~18 tok/s | 可以 | 接近云端小模型 |
| Gemma3-1B / Llama3.2-1B | ~0.8GB | 35~50 tok/s | 舒适 | 只适合闲聊 |
| 7B 级 | ~4.5GB | 5~8 tok/s | 要 12GB+ | 慢到影响体验 |

**技术选型**：`llama.cpp` 的 Android JNI（`llama.android` 官方示例可直接用），
或 `MLC-LLM`（编译好的 so，支持 Qwen 系列，速度更好但集成麻烦）。
**别用**：把 Python 塞进手机（Termux / Chaquopy）——启动 10 秒、耗电、Doze 一掐就死。

### 代价（诚实版）

- 包体 +1~3GB，或者首次启动下载 1~3GB（流量 + 存储）。
- 持续推理时**明显发热、掉电快**（8Gen2 满血跑 4B 约 6~8W）。
- 上下文只能给 4K~8K，现在她在服务器上是 32K+，**长对话会"忘事"**。
- 性格、语气会变：小模型对长提示词的服从度差，`AGENTS.md` 那套细规则会打折。
- 升级模型 = 发新版 App 或再下一次 1GB。

### 我的建议

**不要一上来做 B。** 做成"可选下载"：设置里一个开关「离线模式（下载 1.1GB）」，
装了才在没网时启用 1.7B，有网时仍然走 API。这样 90% 的时间用好的，10% 的场景有兜底。

## 5. 方案 C：手机当服务器（geek 路线，不推荐做产品）

`Termux` + `proot` + Node，直接在手机上跑**现在这套一模一样的 `yu.js` + `dsh`**，
App 连 `127.0.0.1`。理论上零改造。

**为什么不推荐**：Termux 会被 Doze/厂商清理杀掉；Node + dsh 常驻 300MB+；
没有开机自启的可靠办法；用户（你）要会敲命令。**能做，但不是"App"**。
它的价值是：证明"这套代码本身不依赖 x86 服务器"，仅此而已。

## 6. 分阶段落地（建议按这个顺序）

### P0（3~5 天）｜纯 App 能聊、能发语音 —— 质量不降

- [ ] Kotlin 迷你 HTTP 服务（`/api/yu/state|send|stream|upload`）
- [ ] SQLite 存消息与设置；首次启动从 `assets/` 导入默认人设
- [ ] Agent 循环直连 DeepSeek（流式），工具只留 `speak` / `remember` / `remind`
- [ ] 原有 `yu.html` 指到 `127.0.0.1`，验证气泡、表情、语音条、图片全正常
- [ ] 设置面板加「接口地址 / API Key / 人设来源」

**验收**：飞行模式关掉 Wi-Fi 之外的一切，只连 4G，打开 App 就能聊，延迟 ≤ 现在。

### P1（1~2 周）｜断网也有声音

- [ ] 本地 TTS：`sherpa-onnx` VITS 中文（~120MB，离线，接近云端）
- [ ] 本地 STT：`sherpa-onnx` streaming Zipformer（~70MB，边说边出字）
- [ ] 语音消息不再上传，本机转写（预计 **0.5 秒内**，现在是 3.3 秒 + 上传）
- [ ] 定时提醒走 `AlarmManager`（App 被杀也能响）

**验收**：开飞行模式，按住说话 → 她听懂 → 她用本地嗓回你。

### P2（按需）｜离线大模型兜底

- [ ] `llama.cpp` JNI + Qwen3-1.7B（首次下载 1.1GB）
- [ ] 自动降级：API 超时/无网 → 本地模型，回复前加一句"网不好，我小声说"

### P3（不做）
- QQ 桥、多人房间、shell 工具、网页版。

## 7. 一个更省事的中间态：双模共存

不用二选一。让 App **优先本地，能连上服务器就增强**：

```
启动 → 探测 http://<你的服务器>:3000/api/ping（1.5 秒超时）
  ├─ 通  → 用服务器模式（QQ 同步、多人房间、云端记忆都在）
  └─ 不通 → 用本地模式（SQLite 独立跑，消息标 pending，下次连上再合并）
```

好处：你现在这套一行不删；出门没带电脑/服务器到期，App 照样能用。
坏处：两套存储要合并（按 `ts + hash` 去重即可，不难）。

**如果只做一件事，我建议先做这个探测 + 本地模式**，比一步到位重写风险小得多。

## 8. 一张对照表（决策用）

| | 现在（云主机） | 方案 A 纯 App | 方案 B App+本地模型 |
|---|---|---|---|
| 需要一台常开机器 | ✅ 必须 | ❌ | ❌ |
| 需要 easytier / 填地址 | ✅ 要 | ❌ 打开就用 | ❌ |
| 回复质量 | 高（DeepSeek 云端） | **一样高** | 中（1.7B~4B） |
| 断网能用 | ❌ | ❌ | ✅ |
| QQ 能找到她 | ✅ | ❌ | ❌ |
| 多人房间 / 网页版 | ✅ | ❌ | ❌ |
| 月成本 | 机器 ¥/月 + API | 只有 API（¥3~10） | 只有 API（可选 0） |
| 冷启动到能说话 | 开 VPN → 开 App → 等首页 | **点图标 1 秒** | 同左 |
| 开发量 | — | 3~5 天（P0） | +1~2 周 |

## 9. 我的判断

1. **"只凭一个 App"完全可行，而且不是降级**——因为智能本来就在 DeepSeek 云上，
   那台 2 核机器只是个中转站。搬走它，质量一点不掉。
2. **最大的收益不是省钱，是"打开就能说话"**：不用开 easytier、不用填地址、
   不用等服务器醒。这一条对"方便快捷"的贡献，比任何功能都大。
3. **唯一必须付的代价是 QQ**。你要是还想在 QQ 上找到她，就得留一台最便宜的机器；
   要是只在 App 里聊，`yufish.js` 那套可以整体删掉。
4. **真离线（方案 B）当彩蛋做，别当主线**：1.7B 的性格撑不起现在这套人设，
   上下文只有 4K，长对话会明显"忘事"。
5. **先做双模探测**（第 7 节），一周内就能看到效果，且随时可回退。

## 附：几个自己会踩的坑（提前记下）

- **`127.0.0.1` 也是"不安全上下文"以外的情况**：`http://127.0.0.1` 在 WebView 里
  **算**安全上下文（localhost 例外），所以 `getUserMedia` 可用——本地模式下
  录音可以回到网页里做，1.4.1 那套原生录音反而变成"只在远程模式用"。
- **WebView 的 `fetch` 跨端口**：页面在 `127.0.0.1:3000`，接口也在同源，没有 CORS 问题。
- **SSE 在本地没必要**：本地就是一个进程内的循环，用 1 秒轮询 `?since=` 更省电，
  也避免"服务被杀后连接半死"的状态。
- **API Key 存哪**：`EncryptedSharedPreferences`（AndroidX Security），别写进
  `BuildConfig`——APK 能被反编译。
- **人设远程拉取要有兜底**：拉不到/格式坏了就用内置那份，别让 App 白屏。
- **SQLite 的 WAL 模式**：消息写入频繁，不开 WAL 会偶发 `database is locked`。
