# 两个 App：单机版与联机版

> 老板的思路：不做本地模型，像 dsh go 那样 App 自己直连发请求；并且和现在这个"要服务器"的
> 彻底分开，出两个独立安装包；但**小游戏一个都不能少**。
>
> 结论：**可行，而且改动量比想象小得多**——因为她的"游戏脑子"本来就是个客户端，
> 不是服务端。真正要搬的只是那几十个 API 的实现。

---

## 1. 三个发现（决定了这套方案能不能省事）

### 发现一：直连模式在代码里已经存在

`agent-bot/core.js` 196 行，第 128 行就是：

```js
async function llm(messages, { maxTokens = 200, temperature = 0.85 } = {}) {
  const r = await fetch(API, { ... });     // 直接打 OpenAI 兼容接口
```

`agent-bot/config.js` 第 94 行：`LLM_API_KEY` 或 `DEEPSEEK_API_KEY` 都认，
`LLM_AUTH=dsh` 只是**可选项**之一。也就是说"直连发请求"这条路早就通了，
`dsh` 只服务 QQ 桥（`yufish.js`）那一条线。

**所以单机版不需要引入 dsh，也不需要重写大脑**——把 `agent-bot` 这套搬进 App 就行。

### 发现二：她下棋打牌时，是个"客户端"

| 文件 | 干什么 | 关键证据 |
|---|---|---|
| `agent-bot/scenes/gomoku.js` | 下五子棋 | 有 `analyze` / `keyPoints` / `threatReport` / `findMove` 全套本机启发式；最后 `POST /api/go/move` |
| `agent-bot/scenes/card.js` | 打牌 | `fetch(BASE + '/api/action')` |
| `agent-bot/scenes/lingxi.js` | 心有灵犀 | 和浏览器一样读 `/api/lx/*`，只是猜词要模型 |

**她的出招不是模型算的**，是本机算法算的；模型只负责"哼，这步你会后悔"那句台词。
这条比什么都重要：说明游戏规则和"她的智力"是分开的，规则在本机跑不会影响她像不像人。

### 发现三：逻辑层和传输层已经分开了

- `engine.js`（1936 行，牌局规则）只 `require('./content.js')`，没有 fs / http。
- `lx.js`、`yu.js` 都是工厂注入：`module.exports = (ctx) => { const { DATA, json, readBody } = ctx; ... }`
- 也就是说，**只要给它们一个假的存储和一个假的 req/res，它们就能在浏览器里跑**。

真正跟 Node 绑死的只有 `fs` / `path` / `crypto` 三个模块的调用，而且都集中在文件读写那几行。

## 2. 两个包的定位

| | **与鱼（单机）** | **与鱼 · 联机**（现版） |
|---|---|---|
| applicationId | `com.happynav.yu` | `com.happynav.yu.remote` |
| 名字 / 图标 | 与鱼 | 与鱼 · 联机 |
| 打开方式 | 点图标秒开 | 填地址 + 开 easytier |
| 数据在哪 | 手机私有目录 | 服务器 `data/` |
| 模型 key | **你自己的**，App 内加密存 | 服务器的 |
| 谁的脑子 | `agent-bot` 那套（persona + mood + 记忆 + 直连） | dsh（带 shell / 文件 / 搜索工具） |
| 小游戏 | 人机（本机算法 + LLM 台词） | 人机 / 人人 / 联机 |
| 在 QQ 上找到她 | ❌ | ✅ |
| 多设备同步 | ❌ | ✅ |
| 通知 | 本机直接弹 | SSE 守着推 |
| 断网 | 聊天不行，**棋牌能下** | 全不行 |
| 更新 | 独立发版 | 独立发版 |

**两个包互不干扰**：不同 applicationId 可以同时装；不同数据目录互不覆盖；
同一张签名证书，各自升级。

**代价要说清楚**：两份发版、两份 debug。缓解办法是**一份代码两个 flavor**（见第 5 节），
不是复制粘贴出两个工程——那样三个月后规则就会分叉。

## 3. 单机版的架构

```
┌─ APK：与鱼（单机）────────────────────────────────────┐
│                                                        │
│  WebView ── 与联机版共用同一套页面                      │
│    yu.html / index.html / gomoku.html / game / lingxi  │
│        │  fetch('/api/...')  ← 页面一行都不用改         │
│        ▼                                               │
│  本机 API 路由（~200 行）                                │
│    拦截 fetch → 分派给下面几个模块的 api()              │
│        │                                               │
│        ▼                                               │
│  逻辑层（原样复用，约 1.2 万行）                          │
│    engine.js（牌局） content.js（牌面数据）              │
│    lx.js（灵犀） yu.js（房间） go.js（棋，需抽出）        │
│    scenes/*.js + lib/*.js（她的玩法与记忆）              │
│        │                                               │
│        ▼                                               │
│  平台垫片（~250 行，唯一的新基础设施）                    │
│    fs → 原生文件     path → 纯 JS     crypto → getRandomValues │
│        │                                               │
│        ▼                                               │
│  原生层（只做三件事）                                     │
│    ① 文件读写（同步 @JavascriptInterface）               │
│    ② LLM 请求（带 SSE 流，key 不进 JS）                  │
│    ③ 通知 / 录音 / 定时                                  │
└────────────────────────────────────────────────────────┘
```

**一句话概括**：把现在服务器上跑的那套 JS，用一层薄垫片搬进 WebView；
原生只提供"文件、网络、系统能力"三样东西。

### 要实现的接口（都是现成的，照抄行为）

| 前缀 | 来源 | 说明 |
|---|---|---|
| `/api/yu/*` | `yu.js` | 与鱼房间：state / send / stream / upload / act / ping |
| `/api/lx/*` | `lx.js` | 心有灵犀 |
| `/api/go/*` | `server.js` 内联 | 五子棋，**需要抽成 `go.js`**（见 6.1） |
| `/api/room/*`、`/api/state|action|act|restart|stream` | `server.js` + `engine.js` | 牌局 |
| `/api/chat` | `server.js` | 改成走原生 LLM 桥 |

`/api/stream`（SSE）在单机版**不用实现**：数据就在同一个进程里，
页面用 1 秒轮询 `?since=` 更简单、更省电，也避免"服务被杀后连接半死"。

## 4. 五个关键设计决策

### 4.1 逻辑复用：垫片，不重写

| 方案 | 工作量 | 风险 |
|---|---|---|
| **A. Node 垫片**（推荐） | 1 天 spike + 3 天打磨 | 垫片覆盖不到的 API 要现补 |
| B. Kotlin 重写全部规则 | 3~4 周 | 与联机版必然分叉，改一处要改两遍 |
| C. 把 Node 塞进手机（Termux） | 1 天 | Doze 一杀就没，不算产品 |

选 A。**先做一天 spike**：在 WebView 里加载 `engine.js` + `lx.js`，跑一局牌和一局灵犀。
能跑通就一路做下去；跑不通再退到 B 的"只抽纯规则函数"版本（那时损失也可控）。

垫片只垫实际用到的：`fs`（走原生桥）、`path`（纯 JS 的 posix 实现）、
`crypto.randomBytes`（`getRandomValues`）、`Buffer`（base64 两个方向）、
`os.tmpdir`（缓存目录）、`process.env`（空对象）、`module` / `require`。

### 4.2 LLM 走原生，不走页面里的 fetch

三个理由，缺一不可：

1. **CORS**：页面在 `file://` 或 `127.0.0.1`，直连 `api.deepseek.com` 大概率被跨域拦。
2. **密钥**：key 放 JS 里等于放明文，页面上随便一个 `console.log` 就能捞。放
   `EncryptedSharedPreferences`，JS 只说"帮我发这轮对话"。
3. **流式**：SSE 在原生侧解析更稳（`BufferedReader` 逐行读 `data:`），逐段回吐给 JS，
   打字机效果和现在一样。

JS 侧只看到两个方法：

```js
HappyNav.llmStream(payloadJson, callbackId)   // 逐段回调 __llmChunk(id, text)
HappyNav.llmAbort(callbackId)
```

### 4.3 存储走原生文件，不走 localStorage

`localStorage` 只有 5~10MB，聊天记录+牌局存档很快就顶满，而且清了缓存就全没。
`@JavascriptInterface` 的方法是**同步返回**的，所以可以做一个真正的同步 fs：

```kotlin
@JavascriptInterface fun fsRead(path: String): String?      // 不存在返回 null
@JavascriptInterface fun fsWrite(path: String, data: String): Boolean
@JavascriptInterface fun fsList(dir: String): String        // 换行分隔
@JavascriptInterface fun fsDelete(path: String): Boolean
```

`fs.readFileSync` → `fsRead`，`fs.writeFileSync` → `fsWrite`。
一个 200KB 的 JSON 读取约 1~3ms，比 localStorage 的反序列化还快。
`localStorage` 只留给"上次看到第几条""主题"这类 UI 状态。

### 4.4 出招用本机算法，模型只负责说话

这是**不牺牲游戏体验、同时不烧钱**的关键：

| 环节 | 谁做 | 耗时 | 成本 |
|---|---|---|---|
| 选点 / 出牌 / 猜词 | 本机启发式（已存在） | < 30ms | 0 |
| 台词、表情、嘴硬、得意 | LLM（一次短请求） | 0.5~1.5s | 几十 token |

如果让模型算棋：慢（2~5 秒）、会下非法位置（要额外校验）、还费钱。
现在是"算法定胜负、模型定性格"，两边都占。

**只有心有灵犀例外**：猜词本身就是语言推理，必须走模型。但它一轮只猜一个词，
一次 100 token 以内，便宜且天然适合直连。

### 4.5 双人玩法在单机版怎么落地

`engine.js` 第 15 行：`const MAX_PLAYERS = 2;` —— **牌局本来就是两个人**。
所以单机版就是"你 + 她"，不需要改成四人局，逻辑一行不用动。

五子棋同理：现在是她用 `scenes/gomoku.js` 当第二个玩家，单机版她还是第二个玩家，
只是把 `POST /api/go/move` 的目标从 `http://服务器` 换成 `127.0.0.1`。

## 5. 一份代码，两个包（构建方式）

```
core/                          ← 唯一真相：规则、场景、记忆（约 1.2 万行）
├── engine.js content.js      牌局
├── lx.js yu.js go.js         灵犀 / 房间 / 棋
└── scenes/ lib/ core.js      她的玩法与性格

platform/
├── node.js                   fs 真文件、http 真端口 → 给联机版
└── webview.js                fs 走原生桥、fetch 拦截 → 给单机版

apps/
├── server/                   现在的 server.js + agent-bot（联机版后端）
├── apk-remote/               现有壳：只加载 http://服务器/yu
└── apk-local/                新壳：assets 里带 core + platform/webview
```

**改动性质**：主要是给 `require('../core.js')` 这类路径搬家，属于机械性重构，
不是重写逻辑。做完之后：

- 改一条游戏规则 → 两个包同时生效；
- 两个 APK 只是"入口不同"，逻辑完全一致，不会分叉。

构建脚本按 flavor 参数化（现在的 `build-apk.sh` 是 aapt2 + javac + d8 + apksigner，
不引 Gradle）：

```bash
bash build-apk.sh --flavor local    # → happy-nav-local-1.0.apk
bash build-apk.sh --flavor remote   # → happy-nav-1.4.1.apk
```

一个 tag 发两个 asset，Release 里并排放。

## 6. 游戏逐个过一遍（这是老板的硬要求）

### 6.1 五子棋

- **现状**：规则在 `server.js` 第 936~1712 行（内联，约 700 行），AI 在 `scenes/gomoku.js`。
- **要做**：把那 700 行抽成 `go.js`，用和 `lx.js` 一样的工厂签名
  `module.exports = ({ DATA, json, readBody }) => ({ api })`。
- **为什么值得**：不抽出来，单机版就得复制一遍；抽出来之后联机版也更干净。
- **单机版差异**：去掉 `presence`（在线状态）和悔棋"等对方确认"，
  改成"AI 立即同意/拒绝"。

### 6.2 牌局

- **现状**：`engine.js` 纯规则 + `scenes/card.js` 当第二个玩家，走 `/api/action`。
- **要做**：`engine.js` 直接可用；把 `server.js` 里那组 `/api/state|action|restart` 的
  处理函数挪进 `core/room-api.js`。
- **单机版差异**：`MAX_PLAYERS=2` 不变；去掉观战、去掉掉线托管（没有网络）。
- **工作量最大**，因为状态机分支多，要逐条对着联机版跑一遍。

### 6.3 心有灵犀

- **现状**：`lx.js`（401 行）+ `scenes/lingxi.js`（464 行）。
- **要做**：几乎零改动，只把 LLM 调用换成原生桥。
- **单机版差异**：无。

### 6.4 大厅与其他页面

纯静态，原样打包。**唯一要处理的是背景音乐**：12 首 25MB，全塞进 APK 太大。
两个选择：① 打包 3~4 首（约 8MB）；② 首次启动下载（要网，和"单机"有点冲突）。
建议 ①，并在设置里说明。

## 7. 工作量与阶段

| 阶段 | 内容 | 天数 | 验收 |
|---|---|---|---|
| **S0** | 垫片 spike：WebView 里跑通 `engine.js` 一局牌 + `lx.js` 一局灵犀 | 1 | 能出牌、能猜词，不报错 |
| **S1** | 壳骨架：assets 打包、fetch 拦截、原生文件桥、设置页 | 3 | 页面能打开，能发一条消息存下来 |
| **S2** | 聊天：persona + mood + 记忆 + 直连 LLM（流式） | 3 | 她的语气和现在一致，记得住昨天 |
| **S3a** | 五子棋（抽 `go.js` + 人机） | 2 | 能下完整一局，她会嘴硬 |
| **S3b** | 心有灵犀 | 1.5 | 能猜中，能提示 |
| **S3c** | 牌局 | 3 | 能打完一局，结算正确 |
| **S4** | 语音：本地 TTS / 直连 Breeze，录音（已有原生代码） | 2 | 她能说话，能听懂你 |
| **S5** | 双包流水线、数据导入导出、两份 Release | 1.5 | 一个 tag 出两个 APK |

**合计约 17 个工作日**（一个人），但可以切出**第 4 天就能用的 0.1 版**：
能聊、能下五子棋——这已经覆盖 80% 的日常。

## 8. 风险与降级

| 风险 | 概率 | 影响 | 兜底 |
|---|---|---|---|
| 垫片遇到没覆盖的 Node API | 中 | 某个模块跑不起来 | 只垫用到的；报错就补一个函数，不做通用兼容层 |
| WebView 里 tick 循环耗电 | 中 | 后台掉电 | 页面 `visibilitychange` 隐藏即暂停；只有前台才跑 |
| API key 被反编译捞走 | 低 | 别人用你的额度 | key 由用户自己填；`EncryptedSharedPreferences`；不内置共享 key |
| 两个包维护量翻倍 | 高 | 长期成本 | 一份 `core/`；改逻辑只改一处；发版脚本一次出两个 |
| 单机版没有 QQ / 多人 | 必然 | 功能少于联机版 | 定位就是"随身版"，不是替代品 |
| 牌局状态机搬不动 | 低 | 少一个玩法 | 先把棋和灵犀做完，牌局单独评估 |

**最坏情况**：S0 spike 失败 → 退到"只抽纯规则函数"（`engine.js` 的 `Room` 类本来就是纯的，
把它和 fs 解耦即可），代价是多的 3~5 天，但方案不变。

## 9. 需要拍板的三件事

1. **牌局要不要保留在单机版**：它是三个玩法里最重的（3 天），也最依赖状态机。
   不要的话 S3c 砍掉，总工期降到 14 天。
2. **单机版的嗓子**：① 系统 TTS（0MB、离线、机械）② 直连 Breeze（要网、要 key、就是现在的声音）。
   建议②为主、①兜底。
3. **key 谁出**：① 用户自己在设置里填（推荐，安全、责任清晰）
   ② 内置一个共享 key（方便，但等于公开）。

## 10. 明确不做

- 本地大模型（老板已排除）。
- 单机版里的 shell / 文件 / 搜索工具（手机没有沙箱，也不该有）。
- 单机版连 QQ（OneBot 必须常开账号）。
- 把两个包做成"能互相发现"（它们是两个软件，不是主从）。
